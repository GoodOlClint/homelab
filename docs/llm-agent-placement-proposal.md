# Proposed model placement for the homelab agents

November 18, 2026. Recommendation for the two Arc Pro B70 cards in virtual machine 240 and the 256 GB M5 Ultra Mac Studio. This is a placement proposal for the existing services.

| Resource | First placement | Jobs |
| --- | --- | --- |
| B70 card 0 | Keep Qwen3.8-27B running in vLLM with its measured single-card settings. | Interactive requests and routine agent calls. The health, storage and backup agents can gather evidence with their tools and send the model the exceptions to explain. The log correlator and drift detector can use the same model for an initial analysis. |
| B70 card 1 | Use this as an independent worker. BGE-M3 and interactive EmbeddingGemma-2 are candidates to share it with a second model. Size the second model against a mixed-load run. | Keep each index on the model that created its vectors. The Studio is faster for large EmbeddingGemma-2 rebuilds. |
| Mac Studio | Keep oMLX serving its existing clients. Offer a larger local model for explicitly selected jobs once memory headroom, answer quality and the existing network enrollment requirements are verified. | Complex investigations spanning several sources, synthesis over long documents, or private work that benefits from the larger model. Existing EmbeddingGemma-2 indexes continue using their own model. |

Keep agent execution on the planned agent runner, with tool access and approvals at the existing gateway. The accelerator serves model requests. Most of the thirteen example operations agents can share the same chat endpoint. Keep fleet automation on the keyed Proxmox endpoint so it can run while the Studio is busy or offline. Keep the established Claude/Codex pairing for development and independent review where those providers are permitted.

The Intel cards share a host and guest failure domain. Using them independently buys workload isolation and throughput. The guest investigation recorded corrupt direct peer transfers. Its working host-staged two-card run generated 22.7 tokens per second per request at four concurrent requests with roughly 4,000 input tokens each. The recorded single-card baseline was about 40 under comparable conditions. These are decode speeds after the prompt has been processed. [Guest investigation](llm-dual-b70-investigation.md) and [single-card baseline](llm-dual-b70-plan.md).

**First validation.** Move only BGE-M3. Pin the embedding process to card 1 and verify device memory use on both cards. Replay a fixed set of search queries against the existing index and verify the same neighbors, then run a representative index batch alongside four chat requests. Compare time to first token, generation speed and embedding throughput against the current shared-card layout. Include one agent request that calls a tool and one that requires a structured response. Record guest available memory during initialization and under load.

## A dedicated embedding service

The [VM 240 configuration audit](llm-vm240-configuration-audit.md) supersedes the first-step proposal for BGE-M3. BGE-M3 now runs on the second card. EmbeddingGemma-2 and any additional worker remain placement candidates.

The November 18 benchmark supports testing a shared role for card 1. For 180-word inputs sent one at a time, median request latency was 19 ms on the B70 and 27 ms on the Studio. With four concurrent requests of 128 passages each, the B70 served 122 texts per second versus the Studio's 542. The benchmark process held 0.71 GiB of resident graphics memory in one sample. The remaining question is how a second inference worker and interactive embeddings affect each other's latency. The full run and reproduction parameters are in the local benchmark repository at `llm-bench/runs/20261118T203715Z-embeddinggemma-2-bf16-B70-card2.md`.

Validate the second card in VM 240 first. A separate embedding VM is practical if independent upgrades, restarts or resource budgets matter. The two cards already occupy separate hardware isolation groups, 24 and 29. A split would give the embedding guest exclusive ownership of card 1 and retain the same physical host as a shared failure point. Verify host memory headroom before reserving memory for a second guest. [Hardware inventory](llm-dual-b70-investigation.md).

BGE-M3 returns 1,024 values per input and the Studio's EmbeddingGemma-2 returns 768. Give each a keyed route with an explicit model check. Preserve the existing BGE-M3 URL, including its behavior for clients that omit the model. The current production llama.cpp pin recognizes the original EmbeddingGemma architecture. The new model needs the separate `gemma-embedding2` architecture. Trial a newer Intel GPU build alongside the pinned BGE-M3 service. [Pinned architecture registry](https://github.com/ggml-org/llama.cpp/blob/41abbfd599fbdd3470fcae0a1fb6530ad8403cd7/src/llama-arch.cpp) and [upstream EmbeddingGemma-2 conversion](https://huggingface.co/ggml-org/embeddinggemma-2-GGUF).

For EmbeddingGemma-2, compare fixed query and document inputs with the canonical index builder and the current oMLX server. Match preprocessing, input prefixes, output length and normalization. Check vector differences and search rankings on a frozen index, including image-to-text search for clients that use it. Honor any consumer requirement for identical vectors. Then measure an interactive query's 95th-percentile latency (the time within which 95% of requests complete) while the other embedder indexes a batch. The recorded Studio reference is 542 texts per second on roughly 209-token texts with four requests in flight and 128 texts per request. Keep the Studio route available for consumers whose cutover is deferred. [Model card](https://ai.google.dev/gemma/docs/embeddinggemma/model_card_2?hl=en).

## Where NVIDIA PAIR fits

PAIR routes individual requests among paired machines with a compatible engine and the requested model. The proposed use is an optional model endpoint for an agent or workstation that can benefit from another machine's spare inference capacity. Keep the existing Caddy front door and direct embedding routes. NVIDIA lists Apple Silicon among its validated platforms. Intel Arc acceleration, the existing Intel vLLM container, and oMLX need separate evidence. The documented llama.cpp integration requires PAIR's own router. [NVIDIA release and validated hardware](https://www.nvidia.com/en-us/ai-on-rtx/personal-ai-router/) and [engine adoption rules](https://docs.nvidia.com/local-ai/nvpair/architecture/).

The optional Caddy route `/pair/` is disabled in the repository defaults. A small pilot can use VM 240 as a routing-only member and the Studio as the sole provider of a disposable test model on a supported engine. Verify the answering node, a real response through the authenticated route, the outcome with the Studio offline, and pairing after restart across the real network segments. This pilot is independent of moving either embedder. [NVIDIA client and endpoint behavior](https://docs.nvidia.com/local-ai/nvpair/getting-started/) and [existing enrollment decision](decisions/0051-local-inference-on-vm-240-is-ollama-plus-nvidia-pair-behind-caddy-with-per-client-keys-pair-is-opt-in-and-the-macs-join-only-after-a-cross-vlan-enrollment-gate.md).
