# ADR 0050 — ACME DNS-01 TSIG keys are per-host, each granted only its own _acme-challenge name

- **Status:** Accepted (implemented 2026-09-10, audit tranche 2)
- **Date:** 2026-09-10
- **Deciders:** operator + agent
- **Context source:** audit 2026-09-09 finding S3 (issue #20), tranche 1

## Context

ADR 0041 put the fleet's DNS-01 challenge records on a second TSIG key, `acme-key`, scoped by `update-policy` to TXT records. That scope is `grant acme-key wildcard *.<zone>. TXT` on every zone BIND serves, and the same secret (`/infrastructure/acme_tsig_key_secret`) is on every enrolling host: every PVE node, worklab, PBS, PDM, UniFi, and any guest running `cert_client` with the `fleet` issuer. The Infisical `fleet-hosts` policy admits any SAN under `*.<service domain>`.

So one compromised guest holds a key that answers the DNS-01 challenge for `infisical.<domain>`, `pve.<domain>` or any other fleet name, and the `fleet-hosts` issuer hands it a certificate that every node, guest and pod trusts through `ca_trust`. ADR 0041's "scoped" key isolates the zone's *other* record types, not one host from another. The threat is a lateral one — an attacker already on a fleet host — but it is exactly the boundary a per-host PKI exists to draw, and the fix costs no new component.

Fixing it at the issuer instead is not available: Infisical's ACME server has no EAB, so nothing binds an enrollment to a host and the policy cannot be narrowed per client.

## Decision

Each host that enrolls for a `fleet-hosts` certificate holds its own TSIG key, `acme-<host>`, and BIND grants that key exactly the challenge names of the SANs that host may hold:

```
grant acme-<host> name _acme-challenge.<host>.<zone>. TXT;
```

A host with an extra SAN (the nodes carry `pve`, ADR 0041) gets one more `name` grant for it; nothing gets `wildcard`. The secrets are `/infrastructure/acme_tsig_<host>` (host name with `-` → `_`), generated by the `bind9` role from the inventory the way it generates the three keys today, so the primary and secondary render identical `key {}` blocks. Each consumer — `cert_client`'s `rfc2136.ini`, the PBS and PDM `tsig.key` files, `unifi/certificate.yml` — reads only its own host's key from the `secrets` fact. Nothing reads `acme_tsig_key_secret` once the last consumer has moved; the shared key and its `wildcard` grant then leave the BIND template, and the secret is deleted from the vault.

Pinning test (from the issue): from a host holding only its key, an `nsupdate` of a TXT under another host's `_acme-challenge` name is REFUSED, and that host's own `certbot renew --force-renewal` still passes.

## Rejected alternatives

- **Keep the shared key; narrow the Infisical policy per enrollment.** Infisical's ACME server offers no EAB and no per-client policy, so there is nothing to narrow — the policy is per profile, and every host uses the one profile.
- **Accept the risk as ADR 0041's design.** The attacker model (a compromised fleet host) is the one the per-host certificates exist to bound, and every consumer already has a role-owned key file; the change is one secret per host and one grant line per host, not a new subsystem.
- **One key per trust tier (nodes / bootstrap guests / everything else).** Fewer keys, but a tier still lets a guest mint a cert for the vault or the cluster VIP, which is the exact case the finding names.
- **Per-host keys granted with `subdomain` instead of `name`.** `subdomain _acme-challenge.<host>.<zone>.` would also let the key write below the challenge name, which no client needs; `name` is the exact match.

## Consequences

- As built (2026-09-10, #20): the `bind9` role owns the host list — `bind9_acme_hosts` = `bind9_acme_guest_hosts` (proxmox-backup, pdm, unifi) + the nodes from `host-bindings.yaml` (`nodes`, which also get the `pve` grant) + `bind9_acme_extra_hosts` (worklab and the three hand-enrolled appliances: pfsense, ds1821plus, homeassistant) — and generates `acme_tsig_<host>` for each. Grants are rendered only in the service zone. `cert_client` (`rfc2136.ini`), `proxmox_backup` and `pdm` (`tsig.key`) read `secrets.infrastructure['acme_tsig_' ~ inventory_hostname]`; the shared key and its wildcard grant are gone. Pin test passed from proxmox-backup: TXT updates under `_acme-challenge.{pdm,pve,infisical}` REFUSED, its own accepted; forced renewals passed on ms-01b (certbot), PBS and PDM (native). The bind9 pair needed the two passes.
- The three hand-enrolled appliances keep the retired shared key until the operator re-keys them ([docs/operator-hand-steps.md](../operator-hand-steps.md)); their next renewal fails with a REFUSED update until then. `/infrastructure/acme_tsig_key_secret` is deleted by hand after that.
- ADR 0041 is amended by this ADR: its "scoped TSIG key" is now per-host, and its consequence "a third TSIG key for anything but its own scoped grant" reads as "one key per grant" — a new ACME host means a new key and a new grant, never a wider one.
- A renamed or replaced host needs a new key and grant before its first enrollment; a retired host's key and grant come out with the retired-guest sweep, and its vault secret is deleted by hand.
