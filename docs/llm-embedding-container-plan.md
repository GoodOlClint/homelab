# Embedding container migration and guest recovery

## Change for review

Run the existing BGE-M3 embedding model in a digest-pinned upstream llama.cpp Intel server container. Keep the chat image and its settings, the model checksum, embedding alias, first-token pooling, front door and client credentials. Manage the container through the existing embedding systemd service and Ansible role. The proposed decision is recorded in [ADR 0060](decisions/0060-serve-embeddings-from-a-pinned-llama-cpp-intel-container.md).

1. Test the candidate on a separate loopback port, with a read-only model and only the second GPU's devices. Compare the existing and candidate endpoints sequentially for model identity, long and batched requests, vector dimensions, numerical agreement, existing-index retrieval and throughput. Check device residency and a real chat response. Remove the trial container when finished.
2. After qualification, switch the existing unit. Start Docker and containerd only with their data mount available. Keep a rollback copy of the previous unit and the native binary with its shared libraries through the cutover. Exercise an embedding restart and verify chat remains available. Repeat the Ansible run and check the authenticated endpoint. A registry pull or interrupted update must leave the current worker available until its replacement is ready.
3. On a clean guest, provision the model and images before starting services. Remove the native embedder build and its role-owned package preferences from this provisioning path. Test the Ubuntu-supported GPU dependencies still needed by guest diagnostics and the kernel driver. Keep ownership checks on both the persistent data volume and the rebuildable model disk. Refuse mismatched disk identity or an absent weights mount before writing runtime data. Keep the existing authentication flow.
4. Make the normal rebuild verify the fleet inventory refresh and all required inputs before guest replacement. For Ubuntu, use Canonical's latest released Ubuntu 26.04 LTS amd64 server cloud image as the candidate when preparing a rebuild. Verify Canonical's signature on the checksum list and the downloaded image against that list. Record its serial and digest and stage those exact bytes for the plan and apply. Under the existing fleet policy, updating the image is a deliberate pin change (ADR 0016). Preserving the July image is optional. Retain both inference container images, model bytes and required installation packages outside the disposable guest. Use the fleet registry and backup facilities where they support retrieval by the original digest. Confirm capacity, backup inclusion and restoration with empty caches. Preserve the holder's state and verify recovery of service credentials without printing them.
5. Rehearse from an empty guest disk and empty image/model caches. Use a disposable identity, address and disks to avoid conflicting with production. Verify disk layout, a second play with zero unintended changes, reboot, both GPU assignments, authenticated chat and embeddings, denial of anonymous requests, and a search against pre-migration vectors. Back up and restore the retained inputs as a separate check. Moving a working card between guests needs a maintenance window. Replacing the live guest is unnecessary for the rehearsal.

## Boundaries

The persistent deployment and scratch rebuild are separate from the temporary container comparison. Rebuilding the Ubuntu service guest assumes its Proxmox cluster, network, storage, secrets and certificate services are available. Recovery from a physical node failure also requires a working GPU passthrough host and accessible independent backups. Neither scope implies uninterrupted service during a single-host rebuild.

## Acceptance and rollback

- Use the existing 36 labelled queries against the same three published BGE-M3 index generations, each pair of runs sharing a read-only database snapshot. Require no drop in hits at ranks one, five or ten. Across short, long and labelled probes require finite vectors of 1,024 values and minimum cosine similarity of 0.9999 to the native worker. Require at least 90% of the native median batch throughput. The trial sends synthetic requests and reads stored vectors. It performs no index writes. During cutover, pause indexing jobs until the new endpoint passes its external checks. If incompatible vectors were ever written, roll back the affected index generation along with the service.
- Check nonzero resident GPU memory for chat on card 1 and embeddings on card 2, a correct deterministic chat answer, and a four-stream chat run during embedding load. Compare against the same test with the embedding load idle. Confirm correct authentication, the model-name rejection and successful retrieval before resuming indexing.
- Pre-pull the candidate before stopping the old worker. On any failed gate or failure to serve within the unit's five-minute startup budget, restore the old unit and verify both endpoints. Retain the old unit, model, binary, shared libraries and the current guest backup until the rollback and clean rebuild rehearsals succeed. Before a production rollout, test an unavailable replacement digest and an interrupted swap on a disposable instance.
- Keep the current and previous validated releases under operator-controlled retention. Restore and hash-check the recovery inputs before a rebuild can replace the guest. If the fleet registry cannot restore the original digest, retain an OCI image layout (manifest, configuration and layers) in backed-up storage and verify a digest-preserving import into an empty registry. Recheck with each release and before each replacement. A pull-through cache alone cannot establish recovery.
- Stage the rehearsal. Without GPUs, validate provisioning, storage identity and backup restoration. A separately scheduled hardware rehearsal needs the intended GPU devices and equivalent disk assignments, followed by two end-to-end service checks after reboot. Use a disposable account with equivalent policy and separately verify the existing clients' credentials work after restoration. The second full Ansible run must report zero changes. A clean VM-specific Terraform plan cannot substitute for a successful fleet inventory refresh.

## Trial results, November 18

Two fresh containers used the image digest in ADR 0060 and the production BGE-M3 file. Each ran unprivileged with a read-only model, dropped capabilities, a private cache and a port bound to guest loopback. Only the second B70's device nodes were passed through. The file's SHA-256 checksum was `daec91ffb5dd0c27411bd71f29932917c49cf529a641d0168496c3a501e3062c`.

| Candidate setting | Candidate / native median input tokens per second | Lowest cosine similarity between corresponding vectors | Result |
| --- | --- | --- | --- |
| Upstream defaults | 28,010 / 13,678 | 0.99987128 on a long passage | Below the 0.9999 acceptance floor |
| Both Intel oneDNN math paths disabled | 17,333 / 13,709 | 1.0 across short, medium, long and labelled inputs | Passed |

Each timing used ten batches of eight passages. Both candidates returned 1,024 finite values per input and handled a batch of 10,584 input tokens. With the selected settings all 36 labelled query vectors matched the native endpoint exactly, component by component. Using the gateway reader, the native and candidate vectors were compared in a single read-only database snapshot of 121,022 stored chunks across three published generations. Both retrieved the expected file in the top result for 13 queries, top five for 23 and top ten for 29. The first result and rank of the first labelled file agreed for all 36 queries. The trial made no index writes.

Four concurrent chat requests produced 163.5 and 163.3 output tokens per second in aggregate while the candidate was idle. During continuous eight-passage embedding requests, chat produced 161.6 and 161.8 output tokens per second. The GPU process list placed chat on device 0 and the candidate on device 1. Restarting the candidate recovered the embedding endpoint. Chat answered 17 × 23 correctly and the native worker stayed active. The temporary listener was removed. The qualified image remains cached on the weights disk.

The inventory blocker was resolved on 2026-11-18. Correcting stale Terraform state after the retirement of `ms-01b` restored the fleet-wide refresh. All 16 generated guest placements match Proxmox, including `dns2` and `adguard2` on `ms-01c` and VM 240 on `msi`. The existing backed-up holder volume had 76.9 GiB free during the trial. A successful independent restore of the required inputs is still due before rehearsing the rebuild.
