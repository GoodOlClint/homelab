## 2. Decisions (interview 2026-08-25)

1. **ACME DNS-01 for every host with a native client** — PVE nodes (bpg), PBS, PDM, control (certbot `dns-rfc2136`). Directory = `https://infisical.<service domain>/api/v1/cert-manager/acme/applications/<app>/profiles/<profile>/directory`, one application `fleet-hosts`, one profile `fleet-hosts` (root CA, 365-day leaves, EC P-256 / ECDSA-SHA384, `server_auth`), **no EAB** (`skipEabBinding: true`), DNS ownership verification **on**.
2. **The challenge record is written through BIND's dynamic-update path on a second, scoped TSIG key** `acme` (`update-policy { grant acme wildcard _acme-challenge.*.<zone>. TXT; }`, the existing key keeps `zonesub ANY`). Infisical validates by resolving the TXT with `ACME_DNS_RESOLVER_SERVERS` = the BIND VIP (an internal authoritative server, not a public resolver — ADR 0012 unaffected; it also sidesteps AdGuard's negative cache).
3. **Node certs carry `<node>.<domain>` + `pve.<domain>`**, so both Terraform roots point at `https://pve.<service domain>:8006` with `insecure = false`. worklab (not a cluster member) keeps `insecure = true` on the `proxmox.worklab` alias — parked.
4. **PBS fingerprint pins retire** (operator: "drop pins now"): guests, the PVE storage entry, the restore script and the k8s CronJobs verify PBS through the root + SAN. `PBS_REPOSITORY` and the storage entry's `server` become `proxmox-backup.<service domain>` (resolves to the vlan30 leg; nodes reach it over the same 10G bond as vlan20 — the vlan20 leg stays for the Synology iSCSI LUN). `/shared/pbs_fingerprint` stops being written.
5. **Infisical's own cert is the one non-ACME path**: the `infisical` role generates key + CSR on the VM, has the workstation POST it to `/cert-manager/certificates` (API enrollment on the same application), and a **Caddy** container terminates TLS on 443 (`infisical.<service domain>`) in front of the app; **8080 stays** for every machine consumer (the `infisical_url` flip is a follow-on). `SITE_URL` → `https://infisical.<service domain>`. Re-issue when < 30 days remain or the SAN drifts.
6. **Root distribution** = one role `ca_trust` (`/usr/local/share/ca-certificates/homelab-root-ca.crt` from `kubernetes/.secrets/homelab-ca.crt`, `update-ca-certificates`), included by `proxmox_host` and by every guest play, plus a one-shot fleet play `make ca-trust` (both inventories, worklab included).
7. **Scope = the DoD six + control**; UniFi stays self-signed (parked: "UniFi OS cert import spike"); `plex_certificate` is unchanged — no second LE DNS-01 consumer exists, so kickoff item 4 is a recorded no-op.

### Risks and how they are held

- **Pin retirement is fleet-wide** (every guest's backup lane, the PVE storage entry, two CronJobs). Ordering holds it: root trusted everywhere (3) → PBS on a CA cert (7) → pins removed in the same play run; the old pin keeps working until then. Roll back = re-add `--fingerprint` on the storage entry and the `pbs_fingerprint` render (one commit revert).
- **Terraform on the Mac** needs keychain trust (step 5); until then `insecure = false` breaks every plan. The commit for **K/E** lands only after step 5 is verified.
- **DNS-01 timing:** Infisical resolves the TXT at the BIND VIP directly; clients wait the plugin's `validation-delay` (30 s default) — first order per host may take a minute.
- **PDM node config path** is unverified (no CLI setter); build-time fallback is writing `node.cfg`.
- **PBS traffic path** moves from the vlan20 IP to the vlan30 name (same bond, same switch); if throughput regresses, an A record for the vlan20 leg (`pbs-storage.<domain>`) restores it without re-pinning.
- **Infisical is now a runtime dependency of renewals** (already true for the cluster CA); existing certs outlive an outage; Kuma HTTP monitors on the six UIs carry cert-expiry notification (rows added in `uptime-kuma.yml`).

## 4. As-built (2026-08-25) — deviations from §2/§3 and why

Every DoD item holds: `openssl s_client -CAfile kubernetes/.secrets/homelab-ca.crt` → `Verify return code: 0` for `ms-01a|ms-01b|msi|pve:8006`, `proxmox-backup:8007`, `pdm:8443`, `infisical:443`, `control:9443` and `:443`; `curl https://proxmox-backup.<domain>:8007/` → 200 without `-k` from an LXC and from a node; `proxmox-backup-client snapshot list` from a guest with no `PBS_FINGERPRINT`; `pvesm status --storage pbs` active on the FQDN entry with no fingerprint; `make hosts-plan` = No changes with `insecure = false`; `make plan` = no resource changes (see the veth note); renewal proven by a real forced renewal on ms-01a (new serial, `pvenode cert set` hook ran) and `acme cert order --force` on PBS (new serial).

- **Issuer is an RSA intermediate, not the EC root.** Infisical only signs a CSR whose key family matches the CA's (`Requested signature algorithm RSA-SHA256 is not compatible with CA key algorithm EC_secp384r1`), and PVE/PBS/PDM generate RSA keys. `pki_hosts.sh` creates `Homelab Hosts CA` (RSA 4096, 10 years, pathlen 0, installed from the root through `POST /ca/internal/{id}/certificate`) and the profile under it; a profile's CA cannot be changed in place (DB constraint), so a wrong-CA profile is detached from the application, deleted and recreated — which changes the directory URL, so the PBS/PDM roles re-register an account whose directory drifted, and the certbot renewal conf carries the new server.
- **PVE nodes use certbot, not their native client.** Infisical ends the certificate download with `\r\n`; `PVE::ACME` anchors its PEM regex with `$` and rejects it after the DNS-01 validation passed. `proxmox_host/tasks/acme.yml` includes `cert_client` (SANs `<node>` + `pve`, RSA key, deploy hook `pvenode cert set … --force --restart`). `terraform/hosts/acme.tf` keeps only the `insecure` variable; the bpg `proxmox_acme_*` resources were removed from state and the PVE account/plugin files deleted by hand.
- **The DNS plugin runs as `nobody` on all three Proxmox products**, so the key file is `/etc/proxmox-acme/tsig.key` root:nogroup 0640 (not `/etc/pve/priv`, which pmxcfs also refuses to `copy` into without `unsafe_writes` and no `mode`).
- **PBS/PDM CLI quirks:** `acme account register` prompts for EAB on stdin (`printf 'n\n' |`); the first `acme cert order` needs `--force` and exits 0 on a failed task (`failed_when: 'TASK ERROR' in stdout+stderr`); PDM reads `acme/certificate.cfg` — `node.cfg` is ignored; `jq` and `bind9-dnsutils` are installed by the roles.
- **control moved from certbot to the API path.** Infisical's ACME leaves have an empty subject (SAN only); MeshCentral's `getCertificateCommonName` crashes on that. `ansible/tasks/api_certificate.yml` (shared with the `infisical` role) issues a CN-bearing RSA cert; Portainer and MeshCentral both use it. `cert_client` therefore serves the nodes only today.
- **`proxmox-backup-client` hang explained:** with an untrusted cert and no pin it reads the TTY, gets `SIGTTIN` and stops, taking `timeout` with it; the verify task now runs `timeout -s KILL … </dev/null`.
- **`certbot renew --dry-run` is not a proof:** it targets Let's Encrypt staging regardless of `--server`, and `certbot renew` sleeps a random 0–10 min holding the lock. The DoD's "renewal dry-run" is satisfied by real forced renewals.
- **`make plan` shows output-only noise:** agent-reported interface lists move between refreshes (the Infisical VM's Caddy veth after a compose restart, `talos-cp-w`'s `dhcp_ips` toggling between `[]` entries) → "Changes to Outputs", never a resource change. `make refresh` (new target) settles the moment's value; the DoD's "no changes" holds for resources.
- **Cert-expiry alerting** rides the existing `blackbox-tls` (`tls_connect`) job — the six hosts were added as `host:port` targets and the module got `insecure_skip_verify` (the prober trusts no fleet root; `probe_ssl_earliest_cert_expiry` is what `TLSCertExpiringSoon` needs). A duplicate job name I first added crash-looped Prometheus for ~10 min.
- **Idempotency:** `make ansible-all` pass #2 = 0 changed on every host except `plex`, where `infisical_client`'s "Create Infisical config directories" reports changed each run (a pre-P7 mode flap on a tmpfs path; third pass checked below).
- **Kuma cert-expiry rows were not added** — the collection has no `expiry_notification` parameter; the metrics lane covers it instead (`blackbox-tls` job → `TLSCertExpiringSoon`).
- Step order in practice: A → B → C → D → F(key) → E(orders, failed on CRLF) → G/H/I (several iterations for the uid/prompt/`--force`/`certificate.cfg` findings) → nodes via certbot → J → K. The macOS keychain trust was applied non-interactively (`security add-trusted-cert -r trustRoot -k login.keychain-db`) without a prompt.
- Leftovers for the operator: delete the stray empty "Certificate Manager" project from 2026-08-21 (Infisical shows a "multiple Certificate Manager projects" notice; `homelab-pki` is the active one; the fleet identity is not a member of the stray, so it is a UI step: Organization Settings → Products → Certificate Manager → actions menu → delete — 0 certs/syncs/alerts, nothing to export); a `p7-probe` leaf may remain in the vault's certificate list; the old `.internal`-SAN self-signed certs on the nodes are gone.
