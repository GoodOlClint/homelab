# MS-01 Cluster Migration — IaC Change Plan

**Status:** awaiting operator approval (brownfield gate step 4). **Date:** 2026-07-10.

Repoints this repo from the single-node `pve` hypervisor to a 3-node PVE 9 cluster (`crete`, `crete2`, rebuilt `pve`) with Ceph, brings the Proxmox hosts themselves under Terraform from first boot, and rebuilds the service fleet greenfield as static-IP LXCs / docker-on-LXC / VMs per the placement doc.

**Design inputs (canon for the ops side):** `~/okf/playbooks/ms01-cluster-migration.md` (runbook), `~/okf/brainstorm/ms01-cluster-network.md` (network design), `~/okf/brainstorm/workload-placement-vm-lxc-docker.md` (placement), `docs/audit-2026-07-07.md` (IaC gaps), [rebuild-as-routine-design.md](rebuild-as-routine-design.md) (end-state per-service state/rebuild matrix + image policy — ADRs 0015/0016).

## Decisions locked (interview 2026-07-10 + design docs)

## Terraform / Ansible boundary

Terraform (bpg `~> 0.111`, bumped from `~> 0.78`) manages everything the PVE API exposes; Ansible covers the bootstrap the API can't do.

| Layer | Tool | Mechanism |
|---|---|---|
| PVE install | answer file | `answer-<node>.toml` committed; `proxmox-auto-install-assistant` bakes the ISO (checklist in repo) |
| First-boot API token for Terraform | bootstrap script | one small first-boot hook (or `make node-bootstrap <node>`) creates the `terraform@pve` user + token; the only hand-off step |
| Host networking (bond0 LACP on X710s, VLAN-aware vmbr0, VLAN interfaces, MTU 9000 on storage VLAN) | **Terraform** | `network_linux_bond` / `network_linux_bridge` / `network_linux_vlan`, applied over the stable 2.5G mgmt link so the API path is never the link being reconfigured |
| Cluster create/join (**community.proxmox API modules** — ADR 0023, not `pvecm`-over-SSH), Ceph bootstrap (`pveceph install`, MON/MGR/OSD), mgmt re-home + ring/ceph interfaces, keepalived VIP | **Ansible** (new `proxmox_host` role) | create/join is API-driven; the rest is not exposed usefully via the API/provider |
| SDN zones/VNETs (all nodes), cluster options, HA groups/resources, ACME, users/tokens | **Terraform** | existing network module extended. Ceph pool + storage definitions are **Ansible-owned** (B3 boundary — bpg has no storage-definition resource; `proxmox_host` ceph.yml creates pool/CephFS + `pvesm` defs, fleet root consumes the IDs as strings) |
| VMs + LXCs | **Terraform** | existing `proxmox-vm` module + new container support |

New Terraform root **`terraform/hosts/`** with its own state for the host/cluster plane (networking, cluster options, SDN — the Ceph pool moved to the WP2 Ansible role, B3 boundary). Rationale: it must exist before the VM fleet, changes rarely, and a host-networking apply that drops connectivity must not hold the VM project's state hostage. The main `terraform/` project keeps the fleet. (ADR-0002.)

### WP1 — `terraform/hosts/` root + auto-install
- `answer-crete.toml` / `answer-crete2.toml` / `answer-pve.toml`: disk layout (ZFS boot mirror where applicable), initial mgmt IP on the i226-V / VLAN 30, root key.
- Host networking per node: `bond0` (X710 ×2, 802.3ad layer3+4) → VLAN-aware `vmbr0`; `terraform/hosts` puts only the **VLAN 20 storage IP** (MTU 9000) on the bridge. **i226-V** carries VLAN 30 native (install/mgmt bootstrap) + **VLAN 31 tagged (corosync ring0)**; **i226-LM** carries AMT (VLAN 10, ME-tagged) + **VLAN 32 tagged (corosync ring1)**; corosync VLANs 31/32 are dedicated, switch-local on the 2.5G switch (no gateway, not trunked upstream — ADR-0008); one 25G port left for the switched Ceph VLAN 21 link (WP2, ADR 0014). Host mgmt (VLAN 30, web UI/API) + the keepalived VIP are **WP2** — Ansible re-homes mgmt from the i226-V install link to the bond (VLAN 30) and stands up the VIP there (a second VLAN 30 IP on the bond can't be set by `terraform/hosts`, which runs over that link — ADR-0002/0008). AMT is ME-side config, documented not managed. pve variant: 82599ES bond, single I225-V.
- **NIC naming: install the 25G cards BEFORE the answer-file install.** The PVE 9 installer auto-pins every present NIC by MAC via `/usr/local/lib/systemd/network/50-pmx-nicN.link` (`MACAddress=` match) — so a fresh install gives stable `nicN` names immune to later PCIe renumbering, *including the ConnectX ports* as long as the card is seated at install time. Reference the pinned `nicN` names in the answer-file/`interfaces`, not `enpXsY`. (Verified 2026-07: crete2, fresh-installed, was MAC-pinned and survived its card install untouched; crete, upgraded-from-PVE-8, kept unpinned `enpXsY` and lost all networking when its card renumbered the bus — the config still pointed at the old `enp90s0`. Upgraded nodes not being rebuilt need manual MAC `.link` pinning; pve was pinned by hand to `mgmt0/sfp0/sfp1`.)
- **Same rule protects GPU passthrough.** Adding the ConnectX card to pve renumbered its IOMMU groups, breaking the RTX 5000 resource mapping (`iommugroup` 20→21) and stopping the vGPU guests until the mapping was corrected. IOMMU groups, like NIC names and PCI addresses, are stable across reboots but shift when PCIe hardware changes — so seat every card (NIC + GPU) *before* configuring the LLM-VM passthrough. Full passthrough binds by PCI path (`0000:01:00.0`); the optional `iommugroup` pin in the PVE resource mapping can be omitted for extra robustness.
- Cluster options, ACME, `terraform@pve` ACLs once the cluster exists.
- **DoD:** fresh answer-file install of crete → `terraform apply` in `hosts/` converges with zero manual host edits; re-apply is a no-op; host reboot comes up with all planes (bond, VLANs, jumbo `ping -M do -s 8972` to the NAS).

### WP2 — Ansible `proxmox_host` role
- Idempotent cluster create/join via `community.proxmox.proxmox_cluster` over the PVE API (ADR 0023 — `pvecm add --use_ssh` proved unreliable under Ansible in W4), temporary QDevice while 2-node (drop when pve joins).
- `pveceph install` + MON/MGR/OSD creation (idempotent: check before create), keepalived VIP with `pveproxy` track_script + unicast peers.
- **Ceph network split (decide at bootstrap — ADR-0009):** `cluster` network (OSD replication) on the **switched 25G Ceph VLAN 21** (one SFP28 port per node on the Pro-Aggregation — ADR 0014, replaces the FRR mesh); `public` network (client access) on the **10G fabric** so a non-25G node (worklab, later) can be a Ceph *client*. Retrofitting this onto a live cluster is painful — set it at `pveceph init` time.
- New `proxmox` inventory group: `crete`, `crete2`, `pve` (replaces the single-host `inventory/proxmox.yaml`); `update-all.yml` and `monitoring_users` (currently hardcoding a single `proxmox_host` IP in `group_vars/all.yml:34`) go per-node.
- **NUT shutdown clients (landed 2026-08-13, pre-cutover):** `nut_client` role + `nut-clients.yml` (`make nut-clients`), deployed to the live pve + worklab against the pfSense NUT server ([pfsense-nut.md](pfsense-nut.md)). The `nut_clients` inventory group takes the cluster nodes as children (see `proxmox.example.yml`), so crete/crete2 inherit at cutover — run `make nut-clients` after WP2, no new code.
- **netconsole on every node → axosyslog UDP 5515 → OpenObserve `netconsole` stream.** Kernel printk shipped from kernel context over UDP, needing neither the filesystem nor a userspace daemon, so it is the *only* log path that survives a node losing its root disk. Motivating incident: worklab's NVMe dropped off the bus 2026-07-27 and ran ~3 days as a page-cache zombie; the kernel messages naming the cause had to be written to the disk that had just died, so root cause is still unknown and undiagnosable after the fact. Every node in a Ceph cluster carries that same failure mode with a bigger blast radius.
  - **Nodes only — an LXC cannot have its own netconsole.** netconsole is a kernel facility and containers share the host kernel, so the node's netconsole already covers every LXC on it. Since WP4 moves most of the fleet to LXC, expect this to come up; the answer is that guest-level netconsole is neither possible (LXC) nor worth it (full VMs — a guest losing its disk is already visible from the host and PBS).
  - Load late, not via `modules-load.d`: the module needs its egress interface to exist, and `vmbr0` does not at early boot. A systemd unit ordered `After=network-online.target` is correct; the tradeoff is that early-boot messages are missed, which is acceptable for runtime-failure capture.
  - **`console_loglevel` must be raised or the whole thing is theatre.** netconsole is a console driver and only transmits what passes console-level filtering; PVE ships 1–3, so NVMe/EXT4 errors at KERN_ERR (3) never leave the box. The role sets `kernel.printk = 5 4 1 7` via `/etc/sysctl.d/` — level 5 passes `err`+`warn` (the NVMe/EXT4 failure classes) and filters `notice`+`info`. Do not raise it to 7: `console_loglevel` is shared with the VT, so a late `notice` like `sd … Attached SCSI disk` overwrites the getty login prompt and leaves the console stuck on a boot message (observed on worklab 2026-07-30 after briefly running at 7). Applied ad-hoc to pve + worklab pending the role.
  - **A quiet `netconsole` stream is the healthy state — do not alert on staleness.** netconsole carries kernel printk only, so an idle host legitimately sends nothing for days; treating silence as an outage would page constantly. Alert on the *senders* (a Kuma/blackbox check per node) or on a periodic synthetic `/dev/kmsg` heartbeat, never on stream freshness. Corollary: a **manual `rmmod`/`modprobe` cycle** replays the printk ring buffer to the newly-registered console — 2026-07-30, +1034 messages on kernel 7.0.14-4-pve (worklab) but only +3 on 6.8.12-36-pve (pve). A **real boot does not replay**: measured on worklab the same day, a reboot yielded 40 messages with the earliest at 12.3 s, i.e. capture starts when `network-online.target` fires and nothing before it is recorded. Early-boot failures are therefore out of scope for this lane — that is the accepted cost of loading late, and getting it would mean an initramfs-stage netconsole with static addressing. A burst after a manual reload is correct behaviour, not an incident.
  - Off-subnet targets need the **gateway MAC** baked into the module argument — netconsole/netpoll does no ARP resolution. Derive it in the role rather than hardcoding, and treat it as a re-render trigger: a gateway MAC change silently kills transmission with no error anywhere.
  - **Dedicated port, not shared with 5514.** Ingest side landed with this plan entry (`axosyslog.conf.j2` + compose port). The first attempt routed netconsole off the shared 5514 port via parse failure and was wrong: `syslog-parser()` does not reject unframed printk, it parses it as RFC 3164 and eats the first token — verified 2026-07-30, `nvme nvme0: Removing after probe failure` landed in the `syslog` stream as `nvme0: Removing after probe failure`. Silent corruption of exactly the field that names the failing subsystem. The port is the only reliable discriminator. Regression-checked by `scripts/test_axosyslog_routing.py`.
- **Host userspace syslog → OpenObserve (`rsyslog`) — the counterpart to netconsole.** netconsole carries kernel printk only; the daemon logs that actually name a `pvestatd`/corosync/ceph failure ride userspace syslog. **PVE 9 (Debian 13) ships journald-only — no rsyslog installed by default — so the role must `apt install rsyslog` before it can forward** (confirmed 2026-08-10: worklab, a PVE 9 node, had no `rsyslogd` at all; the every-node MS-01 rebuild is PVE 9 and needs the same install). The role then deploys `99-openobserve.conf` forwarding `*.*` over **TCP/RFC 5424 to the services-VLAN axosyslog on 5514** (the `syslog` stream, same path as the VM-fleet `rsyslog_client`). Target is a site binding (`host_bindings.cluster.openobserve_syslog_target`) — the OO VM address is a guest binding, unknowable from `vlans.yaml` in this pre-guest plane — and the whole block is gated on it, so an unset site skips cleanly rather than failing the cluster build. Motivating gap: the pre-rebuild pve host had forwarded to a stale dead services-VLAN address (a long-retired guest IP) for months and nobody noticed, because only netconsole (kernel-only) was still reaching OO — so the 2026-08 `pvestatd` SEGV that greyed the UI was invisible centrally and took an SSH expedition to find. Landed in `proxmox_host/tasks/logging.yml` 2026-08-10. Node-naming caveat: worklab's hostname is `pve` (collides with the primary), so its live forward overrides HOSTNAME→`worklab`; the MS-01 nodes install with unique fqdns (`crete`/`crete2`/`pve`) so they need no override.
- **DoD:** role run twice = zero changes; `pvecm status` quorate; `ceph -s` HEALTH_OK; VIP answers on VLAN 30 and survives killing pveproxy on its holder; `echo test > /dev/kmsg` on each node lands in the OpenObserve `netconsole` stream **verbatim** (leading token intact), tagged with that node's IP, and still lands after a reboot; **`rsyslog` is installed on each node and a `logger` line lands in the OpenObserve `syslog` stream tagged with that node's hostname.**

### WP4 — Fleet rebuild definitions
**Deliberately NOT pre-written:** swapping `vm-configs.tf` to the cluster fleet before the cluster exists would make any apply against live pve propose destroying production guests (today's replace-all drift is bad enough). The new fleet definitions are written at cutover, when the endpoint already points at the cluster.
Placement per the okf doc: **VMs** — infisical (protected), pfsense-test, github-runner, proxmox-backup, unifi, LLM (new). **LXCs** — plex (iGPU), adguard ×2, dns ×2 (BIND primary/secondary), lancache, homepage, mcp, minio, doge. **docker-on-LXC** (nesting) — plex-services, openobserve, docker-legacy. **Retired** — nvidia-licensing, **squid** (its openclaw interception VLAN 140 is deleted — ADR 0017).
- Network contract (ADR 0017): every guest `vlans = ["vlan40"]` (PBS adds vlan20); host role mounts NAS exports on all nodes and LXCs get `shared` bind mount points; pfSense manual steps — admin-port rules on 40, remove VLAN 50/140 interfaces.
- **Default-route trap on PBS's two-legged config — fixed pre-emptively in W6, do not regress.** With `management_vlan` becoming vlan40, PBS's `["vlan40","vlan20"]` leaves vlan20 as the only non-management VLAN, and VLAN 20 has no router (ARP at `.1` is INCOMPLETE). The module now skips gateway-less VLANs when choosing the default-route leg, driven by an explicit `gateway: null` on `storage` in `vlans.yaml`. **That line lives in a gitignored file** — if `vlans.yaml` is ever regenerated or restored from elsewhere, re-add it or PBS boots with no default route, installs nothing, and terraform hangs waiting for the guest agent ([W6 results](pre-migration-state/worklab-campaign-w6-results.md) finding 2).
- **Image rolls (both proven on worklab, W6):**
  - **PBS 4 on Debian 13** (ADR 0025): set the PBS guest's `image = "debian13"` in `var.cloud_images` — the repo suite needs no action, it derives from the guest (below). Proven: PBS 4.2.5 green + idempotent on a Debian 13 cloud image. PVE's iso store rejects `.qcow2`, so the pin renames `file_name` to `.img`.
  - **Fleet noble → resolute (Ubuntu 26.04)**: roll `var.cloud_image`, and `lxc_template` too — `ubuntu-26.04-standard` exists upstream, so the container half is not blocked. No suite flip is needed: resolute ships `libfuse3-4` only and the bookworm client needs `libfuse3-3`, which would have broken every guest's in-guest backup — so the suite is now derived per host instead of being a value someone has to flip at the right moment. Docker on resolute is clean (29.7.2 / Compose v5.4.0).
  - **The suites are DERIVED, not flipped (changed in W6 review round 3b — do not reintroduce a manual flip).** `pbs_repo_suite` and `pbs_client_repo_suite` evaluate from each guest's own `ansible_distribution` facts. A global scalar was wrong in both directions during a roll: `make rebuild <guest>` moves guests one at a time, so the fleet is MIXED throughout, and `bookworm` breaks the first resolute guest while `trixie` breaks every host still on noble — fleet-wide, since `pbs_client` runs in `infrastructure.yml` plus eight service plays. Verified across all four shapes: Ubuntu 24.04 → bookworm; Ubuntu 26.04 VM, Ubuntu 26.04 LXC and Debian 13 → trixie.
  - The LXC template rolls too and was proven on worklab: only the container replaced, the ADR 0015 data volume and ADR 0017 bind mount came back intact.
- **OPEN (ADR 0012 gap on containers) — decide before the LXC fleet is built.** `dns_config` is a VM-only mechanism: its drop-in targets the netplan-generated `10-netplan-<iface>` unit, which containers do not have, and its `netplan apply` handler cannot run in one. It is now guarded to skip on LXC, so plays no longer fail — but **nothing then removes the public bootstrap resolver from a container**, because an LXC's `/etc/resolv.conf` is written by PVE from `containers.tf`'s `dns { servers = var.dns_servers }`, i.e. the full AdGuard-plus-failover list. With most of WP4's fleet on LXC this reinstates exactly the poisoning ADR 0012 prevents. Complication: AdGuard itself is an LXC, so containers cannot simply be given an AdGuard-only list without a bootstrap story ([W6 results](pre-migration-state/worklab-campaign-w6-results.md) finding 11).
  **Deliberately deferred to WP4 (operator, 2026-08-12) — but two facts are already settled, do not re-derive them:** (a) **PVE rewrites a container's `/etc/resolv.conf` on every start** (measured), so an Ansible-written resolv.conf is reboot-transient — the same trap ADR 0012 rejects for `resolvectl`. The only durable control point is the CT `nameserver` setting in `containers.tf`, i.e. Terraform. (b) The live options are therefore: a CT-only resolver list (`lxc_dns_servers`, AdGuard-only, VMs keep the failover for cloud-init), dropping the public failover fleet-wide, or a two-phase build that narrows the CT nameserver after DNS is up. Each needs an answer for how the AdGuard CTs themselves resolve before AdGuard exists.
- **Ansible inventory must carry a per-shape `ansible_user`** — VMs use the cloud-init account, LXCs are root-only by module design (W6 finding 13).
- DNS redundancy (ADR 0003): the two AdGuard instances get identical IaC config; BIND secondary via zone transfer; instances pinned to different nodes via `node_name`; pfSense DHCP hands out both resolver IPs (manual step this round, documented).
- DNS-first (ADR 0006): `dns` role templates BIND zone records from the Terraform inventory + node/VIP list — every guest gets a name automatically; AdGuard forwards internal zones to BIND; homepage/monitoring/inter-service configs use names, not IPs.
- Infisical hardening tightening: UFW + PVE firewall scoped to mgmt/services VLANs, SSH from mgmt only, unattended-upgrades enabled.
- Ansible roles port as-is (SSH is SSH); expected touch-ups: anything assuming a full VM (qemu-guest-agent tasks, kernel/sysctl tasks like the SABnzbd NFS tuning move to the host or get `when: not lxc` guards), plex role gains the `/dev/dri` render group bits.
- Stateful-data checklist (see below) drives per-service restore steps; the **end-state** home for each service's data is the matrix in [rebuild-as-routine-design.md](rebuild-as-routine-design.md) — cutover copy-outs land directly onto the ADR 0015 data volumes.

- **Reverse DNS (PTR) zones — set up once DNS is fully functional (operator, 2026-08-12).** No PTR records exist today (`dig -x` on any fleet address returns nothing), which is why the `netconsole` OpenObserve stream labels hosts by bare IP. netconsole's wire format has no hostname field at all (measured 2026-08-12; see the netconsole userdata entry in `CLAUDE.md`'s What Never To Do), so the collector is the only place a name can come from, and with `use_dns(no)` set globally in `axosyslog.conf.j2` there is nothing to resolve against. Once bind9 serves PTR zones for the fleet subnets, flipping `use-dns(yes)` on the `s_netconsole` source alone (a per-source option, so the 5514 streams keep their sender-supplied hostnames) turns `host` into a name with no sender-side change. PTR is strictly better than the host's own hostname here: PVE node renames are unsupported once guests exist, so the two live nodes both report `pve`, while PTR names are per-address and stay distinct.
- **Fleet apt source is flaky — DECIDED 2026-08-11: [ADR 0021](decisions/0021-fleet-packages-ride-an-apt-cacher-ng-pull-through-cache-with-per-client-fallback-lancache-retires.md)** — apt-cacher-ng pull-through cache with per-client `Proxy-Auto-Detect` fallback (first boot survives cache-absent); Lancache retires. Implementation is follow-on work scoped in the ADR's Consequences. Original problem statement and measurements preserved below for reference. Cloud-init leaves every guest on `archive.ubuntu.com`, whose IPv4 path from here is erratic: measured 2026-08-04 from unifi, three consecutive 6 MB range fetches gave 0 B/s / 4.5 MB/s / 0 B/s, against 8.9 / 9.2 / 3.9 MB/s to `mirror.math.princeton.edu`. Not VLAN-specific (a vlan40-egress guest measured slower than vlan10-only unifi) and not MTU (PMTU 1462 discovered correctly). Guests are IPv4-only on mgmt, so unlike a dual-stack client they cannot fall back to Canonical's much faster IPv6. Symptom is a silent multi-minute stall in `make update` whenever a kernel is in the set — apt has no minimum-rate abort, so a 19 KB/s transfer looks identical to a hang.
  - **Client half staged, not wired:** `ansible/roles/apt_cacher_ng/templates/apt-proxy-detect.sh.j2` is rendered by no task yet, and `apt_cache_proxy_host` is deliberately undefined in every defaults/vars file. The WP2/WP4 wiring (guest cloud-init + proxmox_host) supplies the host from inventory and installs the matching `Acquire::http::Proxy-Auto-Detect` apt.conf.d drop-in. Validated live on the worklab scratch guests 2026-08-11 (cache path + DIRECT fallback).
  - **Rebuild-speed angle (operator, 2026-08-11):** the same WAN-pull cost hits the whole Day-1/rebuild flow, not just `make update` — every guest's cloud-init apt phase AND every node's `pveceph install` pulls packages independently. W4 evidence: nested `pveceph install` across 3 nodes was the single slowest phase of the dress rehearsal (multi-minute, serialized over the no-subscription repo). Across ~3 nodes + ~15 guests the fleet rebuild re-downloads the same package set a dozen-plus times over the flaky path. Two shapes to weigh when we evaluate post-dress-rehearsal: (a) a **pull-through apt cache** (apt-cacher-ng) — purpose-built for `.deb`, cleanest for both guest apt and node `pveceph install`/PVE repos; (b) **adapt the Lancache VM to apt/PVE repos**. Note (operator, 2026-08-11): **Lancache is a retirement candidate** — it was being trialed for Windows Update caching, performed poorly at that, and will be retired UNLESS an apt/other-source use keeps it alive. So this is not "reuse a free existing service" but "give Lancache a reason to exist." Technical fit is plausible: Lancache is DNS-driven sniproxy caching of HTTP GETs, and both `archive.ubuntu.com` (apt) and `download.proxmox.com` (PVE no-subscription) serve over **HTTP**, so adding those to Lancache `cachedomains` + pointing AdGuard at Lancache for those hosts would cache `.deb`/PVE packages fleet-wide with no per-guest proxy config. That single adaptation would both solve rebuild speed AND justify keeping Lancache. Decision fork: adapt-Lancache (keeps one VM, one caching mechanism for games+apt+PVE) vs retire-Lancache + apt-cacher-ng (purpose-built, but a new service). Evaluate both against "does it survive a from-scratch cutover when the cache itself is being rebuilt" — a rebuild-time dependency on a fleet-internal cache is a bootstrap-ordering trap (the cache VM must come up, and its DNS redirection be live, before the guests that depend on it — or first-boot apt must tolerate cache-absent and fall back to the WAN).
