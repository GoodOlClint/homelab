## 6. Round 3 — re-review against the Flux layer (2026-09-10, after rebase onto main)

**What landed on main (ADR 0048, WP8 closed 2026-09-10):** the Kubernetes services plane is reconciled by **Flux from this public repo with no credential** (`kubernetes/flux/`: operator-pushed install, `GitRepository` on `main`, root `Kustomization` with `prune: true`, one `kubernetes/flux/apps/<tree>.yaml` per app with its own ServiceAccount and RBAC, `--no-cross-namespace-refs`, `--no-remote-bases`). Every `${VAR}` comes from the `cluster-bindings` ConfigMap via `postBuild.substituteFrom`, substitution is **strict** (an unbound variable fails the Kustomization), and two ConfigMaps opt out with `substitute: disabled`. **Ansible seeds the allowlisted objects** (`k8s_seed` role, `make k8s-seed`: namespaces with pod-security levels, per-tree RBAC, `cluster-bindings`, generated monitoring ConfigMaps, root-CA ConfigMaps, the bootstrap Secrets `infisical-universal-auth`/`csi-rbd-secret`/`github-app`/`pve-ci-token`/`zot-secret`, the cert-manager intermediate) and runs the in-app tails (`make k8s-apps`). Runtime secrets reach pods only through `InfisicalSecret`s. Every `make talos-<app>` deploy alias is gone; a push to `main` is the deploy, `make flux-reconcile TREE=` only skips the interval, `make flux-check` gates unbound variables and missing requests. A new workload = `kubernetes/<tree>/{kustomization,app|helm,secrets,pvc}.yaml` + `kubernetes/flux/apps/<tree>.yaml` + a namespace entry in `k8s_seed` + `make k8s-seed`; images `${REGISTRY}/<upstream>`, Ingress via Traefik + external-dns, ceph-rbd with `Retain`, requests on every container. **Nothing is parameterised for a second cluster**: kubeconfig, `nodes.json`, root-CA path, Flux namespace, `cluster-bindings` and the universal-auth identity are single-valued. ADR 0048 also rules the `goodolclint-claude` GitHub App must never be Flux's credential (its PEM would sit one privileged-dind hop from every workload). The retired-guest sweep already deleted the `nvidia`/`nvidia_licensing` roles; main's ADR 0050 is per-host ACME TSIG keys, so this stream's ADRs are **0051** (inference) and **0052** (agent plane).

**The round-3 question:** given that this is now *the* way any Kubernetes system in this homelab is configured, does it change ADR 0052? Options:

- **K1 — keep ADR 0052 as written:** agents + MCP are Docker VMs on Proxmox; Kubernetes is not involved. Cost: a second configuration model (Ansible roles + compose) for the agent plane beside the Flux model for services.
- **K2 — agents + MCP as Flux-reconciled workloads on the existing Talos cluster:** `kubernetes/agents/` and `kubernetes/mcp/` trees, their own namespaces/RBAC, `InfisicalSecret`s, the automation isolation expressed as NetworkPolicy + pod-security instead of a VLAN. Contradicts the operator's round-1 instinct ("not mixed into the Talos services cluster") and ADR 0052; the agents pod would run Claude Code/Codex CLIs with a shell and subscription creds inside the services plane; agent-runner's own plan chose a VM.
- **K3 — a second, small Flux-reconciled Talos cluster for the agent plane** (`agents` cluster on msi: one or three CP VMs, its own `automation` VLAN, its own `cluster-bindings`/kubeconfig/universal-auth identity, a second Flux sync path or the same repo with a different root Kustomization). Reuses the exact configuration model; costs the parameterisation work (`k8s_seed`, Makefile, talos.sh are single-cluster today) plus the cluster's own Ceph/CSI or local storage, and RAM on msi (128 GB available).
- **K4 — Docker VMs (ADR 0052) but configured GitOps-style:** compose files reconciled from the repo by a pull agent on the guest (no Flux), keeping "push to main is the deploy" without Kubernetes.

**Questions for the council (round 3):**
1. K1–K4: which, and why, given a solo operator who now has exactly one blessed way to configure Kubernetes and does not want a third?
2. If K3: what is the minimum parameterisation of `k8s_seed`/Makefile/`kubernetes/flux` for two clusters, and does the second cluster share the GitRepository with a second root Kustomization, or get its own sync? Where does its `cluster-bindings` come from?
3. If K2: can NetworkPolicy + pod-security + a dedicated node (taint/toleration on a fourth Talos worker VM on msi) give the isolation ADR 0052 wanted from a VLAN, and what does agent-runner's "runs Claude Code/Codex with a shell" mean in a pod (dind? privileged?)?
4. Does the answer differ between `agents` (untrusted execution) and `mcp` (credential relay, no untrusted execution)? A split (mcp on the Talos cluster as a Flux tree, agents as a VM) is on the table.
5. What in ADR 0051 (inference on VM 240) is affected? Nothing runs on Kubernetes there, but Kuma rows, homepage tiles and the Caddy keys have Flux-side or seed-side homes now.
6. What did the brief miss?

**Operator addition (2026-09-10, after the round-3 opinions):** a second Flux configuration managing a **dedicated MCP-only Kubernetes node/cluster** is acceptable — call it **K3-mcp**: `agents` stays the ADR 0052 VM; `mcp` runs on a single-node (or minimal) Talos cluster on msi with its own Flux root, `cluster-bindings`, kubeconfig and Infisical universal-auth identity. On a node that carries only `mcp`, the node's egress address *is* the gateway's identity, so the pod-SNAT objection to a shared-cluster `mcp` does not apply and the narrow ADR 0030 exception stays narrow. Costs to price against the `mcp` VM: the cluster-parameterisation of `k8s_seed`/`talos.sh`/Makefile/`kubernetes/flux` (which also buys the scratch/rehearsal cluster ADR 0048 wants), one more Talos VM on msi (local storage once msi leaves Ceph; the audit spool is a local PV), image pulls through Zot vs upstream refs (ADR 0022 exemption, since this cluster audits the one Zot lives on), and one more etcd to keep green. The operator also asks for **branch-protection and repo-side deploy-gate recommendations** as a first-class deliverable, since under ADR 0048 a merge to `main` is the deploy.

**Round 3 verdicts (Claude + Codex, 2026-09-10):** both K1 — `agents` a VM, `mcp` a VM, ADR 0052's placement unchanged and its rationale rewritten (flannel = no NetworkPolicy; pod egress SNAT'd to the node; the Flux contract is the wrong shape for these workloads; K3 = 3–4 verified days for a second lifecycle on msi; K4 = a third controller model). Neither council saw the K3-mcp addition; the chairman's assessment is in ADR 0052 (VM now, K3-mcp the named revisit once a cluster profile exists). ADR 0051 unchanged; owners clarified: the VM role owns Ollama/PAIR/Caddy/keys, the homepage tile is a `kubernetes/homepage` commit, Kuma stays Ansible, a pod consumer gets its own `InfisicalSecret` on `/llm`. **Tranche 1 gains:** `make k8s-seed` after `make build llm`; any `${LLM_…}` binding lands in `cluster-bindings` before the tile commit. **Biggest finding of the day:** push-to-main is the deploy and the `main` ruleset has no PR/review/check rule — see [repo-deploy-gate.md](repo-deploy-gate.md). Owed doc fix found by Codex: ADR 0048 §37, `flux_check.py`'s header and the Makefile comment still describe substitution as fail-open/blanking while CLAUDE.md (bd7bbab) records strict mode verified; reconcile the three. Full verdicts in the session scratchpad.

## 7. Tranche 1b — MoE/CPU-offload inference on VM 240 (added 2026-09-11 from the Claude Web handoff; council round 4)

**What changed:** the operator wants useful local inference from the existing box now — MoE models with attention/KV on the GPU and routed experts in system RAM on the CPU — as the stopgap until a dedicated inference box exists. Engine decision: **llama-server (llama.cpp) is the engine**; Ollama stays only as PAIR's supported backend until PAIR grows a llama.cpp adapter (upstream work appears under way), then retires. **VM, not LXC:** msi runs Secure Boot (2026-09-09), and Debian/Proxmox ship the NVIDIA kernel module only as an unsigned DKMS build, which will not load under SB without a MOK enrollment; Ubuntu's `nvidia-driver-580-server` in the guest is signed for its own kernel. ADR 0003's LXC-GPU rejection gets its reason corrected (the vGPU-era instability was the hacked GRID driver + the KSM `BUG_ON`, not "a driver on the host" as a category) and a new one added (SB + DKMS, plus exclusivity with the vfio bind). The LXC shape (host page cache, no guest RAM reservation, native bandwidth) is recorded as the revisit for when msi leaves Ceph and becomes the AI host outright.

**VM 240 respec (module inputs first, then `vm-configs.tf`):** `cpu: host` (AVX2/VNNI visible), 8 vCPUs pinned to P-cores via `affinity` (ids from `lscpu -e` on msi, no E-cores, no SMT siblings), memory ~96 GB with ballooning off, **no 1 GB hugepages in the first pass** (a boot-time reservation is unavailable to everything else on msi; bench them as a separate step), q35 + the existing whole-GPU passthrough. The VM module gains `cpu_type`, `cpu_affinity`, `balloon` (and later `hugepages`) inputs beside `on_boot`, all defaulting to today's behaviour so no other guest changes; the ADR 0016 replace check applies to each.

**Host hand steps (BIOS, msi), in this order:** `ceph osd set noout`; drain talos-cp-c; expect `shutdown_policy=migrate` to move HA VMs; enable XMP with Intel default power limits (never the old unlimited profile); verify `dmidecode -t memory | grep "Configured Memory Speed"` on the host (2DPC boards cap frequency); memtest a full pass before trusting it; on failure drop one step (5600 → 5200) before touching voltage (ceiling for 4×32 GB on 14th gen ≈ 5200–5600 Gear 2, VDD/VDDQ ≤ ~1.35 V, VCCSA ≤ ~1.25 V); check whether the four DIMMs are one matched kit; check `efibootmgr` afterwards (this firmware rewrites `BootOrder`); `ceph osd unset noout`, uncordon.

**RAM budget on msi (128 GB):** 240 at ~96 GB + talos-cp-c 16 GB (OOM-exempt) + OSDs + host leaves no room for `agents`/`mcp` (tranche 2, ~12 GB). Consequence: tranche 2 guests land on an MS-01 unless msi has left Ceph by then — ADR 0052's "all three on msi" becomes "240 on msi; agents/mcp on msi only after the Ceph exit" (consequence note, not a rewrite).

**Model cache:** holder slot 6 is 100 GB on Ceph RBD. gpt-oss-120b (~63 GB MXFP4) fits; a second large model does not, and every model costs 3× raw in the pool. Resize the slot (ADR 0020 appendable holder) to ~250 GB for the bench set, and record that cold load off Ceph scales from the measured 30–49 s per 8 GB. Local NVMe is the msi-leaves-Ceph move.

**Engine + serving:** `llama-server` pinned by release tag with checksum, systemd unit with `OMP`/`-t` = P-core count, `--jinja`, `-fa on`, prompt caching on; Caddy route `/llama/*` (OpenAI-compatible, keyed) replaces the direct `/ollama/*` route as the primary; `/pair/*` stays. Both engines cannot hold the card at once: Ollama under PAIR is limited to small models while llama-server owns the VRAM, and the Kuma states gain a "llama-server up" row. Turing (sm_75) caveats: FA works, MXFP4 kernels fall back on some paths; measure.

**Candidate models (bench set):** gpt-oss-120b (5.1B active/117B, ~63 GB, primary; est. 10–20 tok/s from ~3 GB expert traffic per token against ~70 GB/s real dual-channel bandwidth), GLM-4.5-Air (12B/106B, ~60 GB), Qwen3-30B-A3B (3B/30B, ~18 GB, nearly all on GPU, agent-loop candidate), one **dense ~27B** (Q4 split ≈ 8–12 tok/s, ~3-bit fully on GPU ≈ 25–35 tok/s — quality-for-speed trade, entry kept only if the quality is worth it). Qwen3-235B-A22B skipped (no headroom).

**Definition of done (tranche 1b):** a `llama-bench` table in this doc with pp512 and tg128 for (1) baseline XMP-off, (2) XMP-on, (3) VM tuned (host CPU, pinning), (4) hugepages on/off, (5) the `--n-cpu-moe` sweep to the VRAM ceiling; memtest pass recorded; `make plan llm` shows in-place changes only for the respec; `make ansible llm` second run 0 changed; a keyed `/llama/` chat completion from another guest; `make rebuild llm` → model cache intact; the 1a checks unchanged. The Mac Studio will be faster on the same model; this box's value is CUDA + always-on + the PAIR proof node — say so, do not benchmark against the Studio.

**Deferred:** the LXC shape (MOK enrollment or a signed-module path, msi-leaves-Ceph), a second GPU, vLLM (no Turing FP8/FA2 and PAIR's adapter is not there yet).

**Round 4 verdict (Claude + Codex, 2026-09-11) — §7 amended as follows; the text above stands as the proposal, this list overrides it.** Facts verified on msi the same day: 8 P-cores = CPUs 0–15 (SMT pairs), E-cores 16–31; 125 GB total, 84 GB available with 232 + 240 at 16 GB each; ZFS ARC already capped at 12.5 GiB; two OSDs on msi at a 4 GiB target; `local-zfs` (~466 GB) exists; the DIMMs are **two 2-stick 5600 kits, not a matched 4-stick kit, running at 4000 MT/s** (2DPC JEDEC fallback); ceph-rbd max avail 2.5 TiB; bpg 0.111.1.
1. **VM 240 = 80 GB, not 96** (`memory_mb = 81920`, no balloon); vfio pins all guest RAM at start, so the figure is committed at boot. Host acceptance gate: ≥ 24 GiB `MemAvailable` on msi under the worst accepted load, no swap growth, no OSD flap, Ceph latency within threshold. 240 is the intended OOM victim before any OSD; state that in the role.
2. **`cpu_type = host`** (module input exists); **`cpu_affinity`** new input; start with one hardware thread per P-core (Claude: 6 P-cores so two stay with the two OSDs + corosync; Codex: 8) — **6 first, 8 as a bench row**. `on_boot` new input, **false until the restart/pressure gates pass**. `memory_floating_mb` new input default 0. No hugepages/NUMA inputs in 1b. bpg lands cpu/memory edits by stop+start: "in-place" = one reboot of 240.
3. **Weights live on a per-VM `extra_disks` volume on msi `local-zfs`** (disposable, re-downloaded with checksum on `make rebuild`; the GGUF is not ADR 0015 state). Holder slot 6 stays 100 GB for PAIR identity + Ollama's small models. No 250 GB RBD resize.
4. **XMP is outside the software acceptance path**: JEDEC first; the XMP row is an optional maintenance event (verify the kit and rated timings first, Ceph healthy/no backfill, HA parked, talos-cp-c drained, 240 stopped, `noout`, Intel default power limits, **≥ 4 memtest passes or overnight**, drop frequency before voltage, verify SB/kernel/BootOrder/`dmidecode` after, sustained CPU+RAM then CPU+GPU soak, unset `noout`, restore). Estimates are labelled hypotheses, not predictions; at 4000 MT/s expect the low end.

Gate for gpt-oss-120b to stay in the set: tg128 ≥ 12 tok/s **and** an agreed pp8k budget.
