## What Never To Do

- **Never benchmark or script Gemma 4 through Ollama without `"think": false`** — it is a thinking model, so with the flag unset every generated token lands in the `thinking` field and `response` comes back empty while `eval_count` looks fine
- **Never install a locked Python app with `uv tool install`.** It resolves fresh and ignores the project's `uv.lock`, and a crash-looping `Restart=on-failure` unit in `activating` still satisfies `state: started`, so the play reports 0 changed. Clone at the tag and `uv sync --frozen`.
- **Never generate an OpenObserve password with `openssl rand -hex`, and never ask OSS OpenObserve for a non-`admin` role.** Its user API rejects a password without upper case, lower case, a digit and a special character, and it answers any other role with `Custom roles not allowed` (both 400, both censored by `no_log`). The `mcp` role generates `Mcp-0<hex>`.
- **Never size VM 240 from process RSS, and never let an embedder load with a bigger micro-batch than its inputs need** — the xe driver places GPU buffers that miss VRAM in GTT, guest RAM visible only as `drm-total-gtt` in `/proc/<pid>/fdinfo/*`, and beside vLLM at 0.90 a bigger micro-batch's flash-attention scratch cannot be reserved and llama-server aborts. `-ub 2048` and `--cache-ram 0` are the rule and `vllm.service` gates on `systemctl is-active llama-embed`
- **Never move containerd's content store and restart only docker** — the store is containerd's, and `data-root` in `daemon.json` does not cover it, so relocating it takes a `/var/lib/containerd` symlink *and* a containerd restart (`containerd` then `docker`). Restart docker alone and every pull dies `failed to lease content: ... blob not found`.
- **Never treat vLLM's `/health` as proof the engine is working** — it is the API server's liveness, not the engine core's: a wedged engine keeps answering 200 while no request completes, and the hung request is never logged. `vllm-liveness.timer` is the real check, restarting the engine after **two** consecutive failures; do not run `make ansible llm` against 240 while an index build is in flight
- **Never gate a post-restart probe of VM 240's engines on `/health`** — `vllm.service` answers `/health` while `ExecStartPost=vllm-warmup` is still compiling batch shapes (`activating (start-post)` for ~90 s), so a probe that starts on `/health` reads the warmup as a hang. Wait for `systemctl is-active vllm` to return `active`; the same trap applies to `llama-embed`'s `ExecStartPost` warm-up
- **Never raise VM 240's vLLM budget to `--gpu-memory-utilization 0.88 --max-num-seqs 64`, and never start a second XPU process while one is initialising** — the first OOM-kills `VLLM::EngineCore` during init through host memory pinned by GPU-mapped buffers, which `xpu-smi` folds into its *device* figure, and a second XPU process fails an engine init through the shared triton/NEO compile cache. The served budget is `0.90 / 8 / 4096`, and `vllm.service` gates on `llama-embed`'s `/health`
